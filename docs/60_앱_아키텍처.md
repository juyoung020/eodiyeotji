# 어디였지: 앱 아키텍처

> 목표: **빠르고(버벅임 없음), 손이 덜 가는** 차량용 앱.
> 무거운 계산은 Rust 네이티브 코어에서 하고, Kotlin은 화면 표시와 Pleos SDK 연결만 맡는다.

## 1. 설계 원칙

| 원칙 | 의미 |
|---|---|
| **UI 스레드는 절대 막지 않는다** | 계산, DB, 검색은 모두 Rust 코어에서 백그라운드로 처리. Kotlin은 결과만 그린다 |
| **네트워크를 기다리지 않는다** | 지도 타일, 기록, 검색 인덱스를 모두 기기 안에 둔다 (오프라인 우선). 서버는 LLM 요약과 코스 공유만 담당 |
| **사용자가 아무것도 안 해도 된다** | 시작 버튼 없이 자동 기록. 설정 없이 바로 동작 |
| **운전 중에는 말로만** | `CarUxRestrictions` 기준으로 주행 모드와 정차 모드 화면을 나눈다 |

## 2. 전체 구조

```
┌──────────────────────────── Android App (Kotlin) ────────────────────────────┐
│  UI: Jetpack Compose (Pleos 공식 샘플과 같은 스택)                            │
│   ├ 주행 모드: 음성 + 큰 카드 1장        └ 정차 모드: 타임라인 · 지도 · 피드   │
│  Map: MapLibre Native (C++ / GPU 벡터 렌더링) + 기기 내 PMTiles 지도 파일     │
│  Pleos SDK 어댑터: FusedLocation · NaviHelper · Vehicle · STT · TTS           │
│        │ (위치·이벤트를 묶음으로 전달)            ▲ (결과: 요약 · 경로 · 검색) │
└────────┼──────────────────────────────────────────┼──────────────────────────┘
         ▼              UniFFI (Kotlin ↔ Rust 바인딩 자동 생성)               │
┌──────────────────────────── eodi-core (Rust) ─────────────────────────────────┐
│ ingest     위치 노이즈 제거 · 배치 수집                                       │
│ trip       주행/정차 구간 나누기, 머문 곳 판정 (정차 시간 + 도어 이벤트)      │
│ geo        경로 단순화(Douglas-Peucker), 거리 계산, 공간 인덱스(R-tree)      │
│ store      SQLite(rusqlite, 내장) + R-tree + FTS5 전문 검색                  │
│ search     날짜 · 장소 · 동승자 · 태그 · 자연어 키워드 → 100ms 안에 결과     │
│ recall     지금 위치 근처의 "예전에 간 곳" 후보 계산 → 지오펜스 등록 목록   │
│ course     코스 내보내기 · 구간 분할 (NaviHelper 경유지 최대 2개 제약 대응)  │
└───────────────────────────────────────────────────────────────────────────────┘
         │ (하루 기록 요약 요청 / 자연어 질문 → 검색 조건 변환)
         ▼
   LLM 서버 (요약 · 질문 해석만 담당, 검색 자체는 기기 안에서)
```

## 3. 왜 이렇게 나눴나

### Kotlin은 꼭 필요한 곳에만
- Pleos SDK 5종이 모두 Kotlin/Java 라이브러리라서 SDK 호출은 Kotlin에서 해야 한다.
- 화면은 Compose로 만든다. 공식 샘플과 같은 스택이라 Pleos 디자인 가이드와 맞추기 쉽다.

### Rust 코어가 맡는 일 (버벅임의 원인을 없애는 부분)
| 기존 앱이 느린 이유 | 우리 방식 |
|---|---|
| 위치 점 수만 개를 UI 스레드에서 그대로 그림 | Rust에서 경로를 단순화(점 수 90% 이상 감소)한 뒤 GPU로 그림 |
| 검색할 때마다 서버를 호출 | 기기 안 SQLite FTS5 + R-tree로 즉시 검색 |
| 지도 타일을 매번 네트워크로 받음 | PMTiles 한국 지도를 기기에 저장 (오프라인) |
| JVM 객체를 많이 만들어서 GC가 멈춤 | 데이터 처리는 Rust 메모리에서. Kotlin에는 결과만 넘김 |
| JNI를 점 하나마다 호출 | 위치를 **묶음(batch)**으로 한 번에 전달 |

### 지도 렌더링은 MapLibre Native
- C++로 만들어진 GPU 벡터 지도 엔진이라 네이티브로 빠르게 그린다.
- Rust로 지도 렌더러를 직접 만드는 것(maplibre-rs 등)은 아직 실험 단계라 4주 안에 안정적으로 만들기 어렵다.
- **경로 계산과 데이터 처리는 Rust, 그리기는 MapLibre**로 역할을 나눈다.

### LLM은 "요약과 해석"만
- 하루 요약: 기록이 끝나면 한 번만 호출하고, 결과는 기기에 저장해 둔다.
- 질문 해석: "작년 여름 바다" → `{기간: 2025-06~08, 태그: 바다}` 같은 검색 조건으로 바꾸는 일만 한다.
- 실제 검색은 Rust 코어가 기기 안에서 한다. 그래서 LLM 응답이 느려도 결과는 빨리 나온다.
- 자주 쓰는 질문 형태(날짜, "지난주" 같은 표현)는 LLM 없이 규칙으로 바로 처리한다.

## 4. 사용자 편의 설계

| 상황 | 화면 / 동작 |
|---|---|
| **시동을 걸 때** | 자동으로 기록 시작. 회상할 내용이 있으면 카드 1장만 보여줌 ("1년 전 오늘…") |
| **주행 중** | 화면 조작 최소화. "어디였지?" 음성 → 결과를 TTS로 읽어줌 → "안내해줘" 한마디로 내비 연결 |
| **예전에 간 곳 근처를 지날 때** | 짧은 음성 한 번. 하루 횟수를 제한하고 내비 안내와 겹치지 않게 함 |
| **정차 / 주차 중** | 타임라인, 그날의 지도, 검색, 코스 공유를 모두 사용 가능 |
| **공유할 때** | 집 · 회사 근처 구간은 자동으로 가림. 미리보기를 확인한 뒤 올림 |

- 터치 영역은 크게, 한 화면에 핵심 행동 하나 (Pleos UI 디자인 가이드 기준)
- 첫 실행 때 권한 요청 외에는 설정 화면을 거치지 않음

## 5. 성능 목표 (측정해서 확인할 기준)

| 항목 | 목표 |
|---|---|
| 앱 시작 → 첫 화면 | 1초 이내 |
| 지도 이동 · 확대 | 60fps 유지 |
| 기기 안 검색 | 100ms 이내 |
| 하루 경로 그리기 (점 1만 개 기준) | 단순화 후 16ms(1프레임) 이내 |
| UI 스레드 블로킹 | 0 (StrictMode로 확인) |

## 6. 프로젝트 구조

```
app/src/main/java/app/eodiyeotji/      두 판(car·phone) 공통
  ├ core/EodiCore.kt      Rust 코어 입구 (모든 호출은 백그라운드 스레드) + 화면에 넘기는 불변 모델
  ├ platform/             판마다 다른 것의 인터페이스: 위치·주행 신호·내비·음성·기록 권한
  ├ record/               자동 기록: 주행 신호 → 위치 묶음 → EodiCore.ingest
  │                         RecordingService(포그라운드) · 부팅 시 자동 시작 · 첫 실행 권한 게이트
  └ ui/                   timeline(정차 모드 첫 화면) · home(코어 상태 줄) · theme
app/src/car/              차 판: Pleos SDK 어댑터(pleos/) · 기어·시동 신호(CarPropertyManager) · CarUxRestrictions · PlatformModule
app/src/phone/            폰 판: Android 위치 · 위치로 주행 감지(Rust drivedetect) · 지도 앱으로 안내 넘기기 · Android 음성 · PlatformModule
core-rs/src/
  ├ ffi.rs                Kotlin에 공개하는 함수 (UniFFI)
  ├ store.rs              EodiStore: SQLite 저장, 주행·머문 곳 계산 결과와 날짜별 요약을 증분 갱신
  ├ trip.rs · geo.rs      주행 나누기 · 머문 곳 · 경로 단순화 · 거리
  ├ course.rs             코스 구간 분할 (NaviHelper 경유지 2개 제한)
  └ drivedetect.rs        폰 판 주행 감지 (속도·머문 시간으로 시작·끝, 저전력/고정밀 위치 전환)
scripts/                  setup-dev · emu(에뮬레이터) · vc(차량 상태) · replay(시연 경로 재생)
server/                   LLM 요약 · 코스 공유 API (2차 단계)
```

빌드 흐름: `./gradlew installCarDebug`(폰 판은 `assemblePhoneDebug`) 한 번이면 Gradle이 `cargo ndk`로 x86_64(에뮬레이터)·arm64(실차) `.so`를 만들고, UniFFI로 Kotlin 바인딩을 생성한 뒤 앱을 빌드한다 (결과물은 `app/build/` 아래).

### 자동 기록 흐름

```
기어 P→D (2초 유지) 또는 시동 ON ──▶ markDriveStart ─▶ FusedLocation 구독 시작
   주행 중: 위치를 모아 10초 또는 30개마다 ingest (Rust가 노이즈 제거 후 SQLite에 저장)
기어 D→P (5초 유지) 또는 시동 OFF ──▶ 남은 묶음 ingest ─▶ markDriveEnd ─▶ 구독 중지 (주차 중에는 차량 신호만 듣는다)
타임라인 화면 ◀── EodiCore.changes ◀── day_summaries / day_detail (Rust가 시간순·날짜별로 계산해서 준다)
```

폰 판은 기어·시동 대신 위치로 주행을 판단한다 (Rust `drivedetect`): 시속 15km 이상이 20초 넘게 이어지고 200m 넘게 벗어나면 시작
(시작 시각은 출발한 순간으로 거슬러 잡고 그사이 위치도 저장), 반경 80m 안에 4분 넘게 머물거나 위치가 10분 끊기면 끝.
서 있을 때는 1분 간격 저전력 위치만 받고, 움직임이 보이면 2분 동안 1초 GPS로 확인한다. 길 안내는 설치된 지도 앱(네이버·카카오·티맵·구글)으로 넘긴다.
